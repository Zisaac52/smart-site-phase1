# 智慧工地 AI 视觉安全闭环管理系统 — 第一阶段交付说明

> 版本：V1.0  
> 日期：2026-06-02  
> 基于：RuoYi-Vue v3.9.2 SpringBoot3

---

## 一、系统概述

第一阶段完成了**施工安全监管基础平台**的数据底座建设，实现人员实名制体系、角色规则体系、资质证件体系、审核流程体系、打卡记录体系。

当前阶段不涉及 AI 识别、视频流、摄像机自动打卡等能力，后续阶段在此基础上扩展。

---

## 二、功能模块

侧边栏「人员管理」目录下包含 6 个子模块：

| 模块 | 说明 | 对应表 |
|---|---|---|
| 人员档案 | 施工人员实名信息管理，含角色分配 | `tb_worker` |
| 角色规则 | 定义角色及其打卡/资质规则 | `tb_worker_role` |
| 资质证件 | 人员证件上传、有效期管理 | `tb_worker_cert` |
| 人脸信息 | 人脸照片采集（特征值字段预留 AI） | `tb_worker_face` |
| 审核记录 | 人员/资质审核流程，审核结果自动回写 | `tb_worker_audit` |
| 打卡记录 | 签到/签退/点到 打卡记录 | `tb_worker_checkin` |

## 三、完整业务流程

### 3.1 人员入库

```
1. 管理员登录 → 人员档案 → 新增
2. 填写：姓名（必填）、手机号（必填，自动校验格式）、身份证号（必填，自动校验格式）
3. 输入身份证号后自动推断性别（第17位奇=男/偶=女），可手动修改
4. 选择单位类型（管网/第三方/施工方）
5. 选择人员状态（在场/离场/禁用）
6. 确定 → 人员创建成功，默认待审核（audit_status=0）
```

### 3.2 角色分配

**技术实现：**
- 规则校验统一入口在 `TbWorkerServiceImpl.validateRoleRequirements()` 中，使用 `@Transactional`
- Controller 层（`saveRoles`）仅负责接收请求 → 调用 Service，不包含业务逻辑
- 后续 checkin 等模块可复用同一校验入口

**约束策略（弱约束）：**
- 角色照常分配保存，不阻断操作
- 证件有效性严格判断：必须 `audit_status='1'`（已通过）且未过期，待审核/已驳回/已过期的证件均不算有效资质
- 缺少有效证件时：前端弹出黄色警告 + 该人员 `audit_status` 被退回 `'0'`（待审核），后续打卡等操作会被拦截
- 证件齐全 → 正常保存，不影响审核状态

**操作流程：**
```
1. 人员档案 → 点击某人的「修改」
2. 弹窗中「分配角色」多选框 → 列出所有角色规则
3. 勾选角色（支持多选，一人可兼多角色，如「项目经理」+「安全员」）
4. 系统自动校验角色规则（Service 层统一入口）：
   - 角色 need_cert=1 → 检查该人员是否有通过审核且未过期的对应证件
   - 缺少 → 黄色警告「缺少资质：XX角色 需要 XX证件」+ 人员状态退回「待审核」
   - 齐全 → 正常保存
5. 人员列表「角色」列实时显示已分配的角色名称
```

### 3.3 证件上传

```
1. 资质证件 → 新增
2. 选择人员（按姓名搜索下拉）、证件类型（身份证/安全员证/电工证等）
3. 填写证件编号、发证日期、过期日期
4. 上传证件图片（支持 jpg/png/pdf）
5. 保存 → 证件默认待审核
```

### 3.4 人脸采集

```
1. 人脸信息 → 新增
2. 选择人员、上传人脸照片、选择采集时间
3. 人脸特征值字段（face_feature）保留给后续 AI 阶段
```

### 3.5 审核流程（闭环）

审核模块不仅是"审核记录台账"，而是真正的流程引擎——审核动作会驱动业务主表状态变更。

**技术实现：**
- 回写逻辑在 `TbWorkerAuditServiceImpl` 中，`insertTbWorkerAudit()` / `updateTbWorkerAudit()` 使用 `@Transactional` 保证事务一致性
- 新增/修改审核记录时，同时根据 `bizType` 更新对应主表的 `audit_status`：
  - `bizType=worker` → `UPDATE tb_worker SET audit_status=? WHERE id=?`
  - `bizType=cert` → `UPDATE tb_worker_cert SET audit_status=? WHERE id=?`
- Controller 层为纯入口，不包含业务逻辑

**操作流程：**
```
1. 审核记录 → 新增
2. 选择业务类型：
   - 「人员」→ 只需选关联人员（bizId 自动等于 workerId，前端隐藏业务数据ID）
   - 「资质」→ 需选关联人员 + 业务数据ID（对应证件ID）
3. 选择审核结果：待审核 / 已通过 / 已驳回 / 已过期
4. 填写审核意见（通过时填"资料齐全"，驳回时必须写原因）
5. 保存 → Service 层在同一事务内执行：
   a. 插入审核记录（留痕）
   b. 更新对应人员或证件的 audit_status（驱动业务状态）
6. 验证：
   - 人员档案/资质证件页面中的审核状态标签立即变化
   - 修改已有审核记录 → 主表状态同步更新
   - 打开人员修改弹窗 → 关联数据区实时显示最新审核记录
```

### 3.6 打卡记录

```
1. 打卡记录 → 新增
2. 选择人员、打卡类型（签到/签退/点到）、打卡时间
3. 选择打卡方式（手动/公众号/AI）、可选上传现场照片
4. 支持按人员、打卡类型、时间范围搜索和导出：
   - 搜索栏「日期范围」选择起止日期
   - 后端 Mapper 使用 check_time >= beginCheckTime AND check_time <= endCheckTime 区间查询
   - 前端通过若依标准 params 机制传参（params.beginCheckTime / params.endCheckTime）
5. 安全帽/反光衣字段已建表，后续 AI 阶段启用
```

## 四、数据校验规则

| 规则 | 说明 |
|---|---|
| 身份证唯一 | 新增/修改时后端检查，重复则拒绝并提示 |
| 手机号格式 | 前端校验 11 位手机号格式，失焦即提示 |
| 姓名必填 | 表单 required 校验 |
| 身份证自动推断性别 | 18 位身份证第 17 位奇=男/偶=女 |
| 人员归档（软删除） | 设置 del_flag='2' + status='2'，所有关联数据保留可审计 |
| 归档后操作限制 | 证件/人脸/审核/打卡/角色分配 的 新增+修改 接口均通过 isWorkerActive() 前置校验，已归档人员拒绝操作 |
| 历史数据展示 | 证件/审核/打卡列表中，已归档人员显示为「XXX(已归档)」 |

## 五、表结构关系

```
tb_worker（人员档案）
  ├── tb_worker_role_rel（多对多关联）
  │     └── tb_worker_role（角色规则：need_cert / need_sign_in / need_hourly_check …）
  ├── tb_worker_cert（资质证件：cert_type / cert_no / expire_date / cert_img）
  ├── tb_worker_face（人脸信息：face_img_url / face_feature / collect_time）
  ├── tb_worker_audit（审核记录：biz_type / audit_status → 回写源表）
  └── tb_worker_checkin（打卡记录：check_type / check_time / check_method）
```
